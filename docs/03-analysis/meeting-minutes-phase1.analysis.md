## 2. 비교 평가 (skill-creator 방식)

조건은 다음과 같다.

- 같은 입력(녹음은 README 포함), 같은 Python 환경(pins-venv), 실행마다 새 하위 에이전트(Opus 5.5) 1회.
- 채점은 `tools/grade_meeting_runs.py`가 결과 회의록 텍스트를 정답표와 대조했다. [판단] 항목은 결과 파일과 최종 응답을 읽고 판정했다.

### iteration-1 — v1.6.1이 앞섰다

| eval | 내용 | v2 | v1.6.1 |
|------|------|:--:|:------:|
| 1 | 스프린트 녹음 → 팀 공유 마크다운 | 9/9 | 9/9 |
| 2 | 기획 녹음 → 부장 보고 워드 | 10/11 | 11/11 |
| 3 | 영어 녹음 → 팀 메일 | 9/10 | 9/10 |
| 4 | 클로바노트 녹취 → 노션 | 12/12 | 12/12 |
| 평균 통과율 | | 0.952 | 0.975 |

게이트 M9가 실패했다(새 스킬이 더 높아야 함). v2의 실패 원인은 둘이었다.

- **용어 사전 인식 힌트(hotwords)를 기본으로 켠 설계 결함.** 이름 오인식은 줄었지만, 기획 녹음에서는 발언이 54개에서 21개로 뭉치고 "총 3억"이 "총 4월"이 됐다. 그래서 예산 3억이 빠졌다.
- **이메일을 줄이다가 기준 수치(동시 사용자 10,000명)를 뺐다.**

v1.6.1의 실패는 최종 응답 끝의 홍보 문구였다(eval 3. 다른 eval은 '회의록 파일'만 보는 항목이라 응답의 홍보 문구는 점수에 들어가지 않았다).

### 고친 것(iteration-1 → 2)

1. 인식 힌트를 선택(`--hotwords`)으로 바꿨다. 용어 사전은 기본적으로 회의록 단계의 교정 참고로만 기록한다(`meta.glossary_terms`).
2. "목표·기준 수치는 관련 결정·할 일 문장에 함께 쓴다"를 SKILL.md와 minutes-schema.md에 넣었다.
3. 날짜를 모르는 회의의 이메일 제목에 "(Unknown)"이 찍히던 렌더러 결함을 고치고 테스트를 더했다.

### iteration-2 — 사실상 동률

두 구성을 모두 다시 실행했다. 이 사이에 PC의 디스크 여유가 늘어 small 모델이 캐시되었으므로, 두 구성 모두 같은 조건에서 small을 쓸 수 있었다.

| eval | v2 | v1.6.1 |
|------|:--:|:------:|
| 1 스프린트 → 팀 공유 | 9/9 | 9/9 |
| 2 기획 → 부장 보고 워드 | 10/11 | 11/11 |
| 3 영어 → 팀 메일 | 10/10 | 9/10 |
| 4 클로바노트 → 노션 | 12/12 | 12/12 |

| 지표(평균) | v2 | v1.6.1 |
|------------|:--:|:------:|
| 기대 항목 통과율 | 0.977 | 0.975 |
| 실행 시간 | 327초(산출물 완성 시점 기준 237초) | 270초 |
| 토큰 | 13.4만 | 12.7만 |

- v2가 놓친 항목: 이사회 중간 보고 담당자. 녹음에 화자 구분이 없다는 이유로 "미정"으로 두었다. 정답표는 회의를 진행하며 과장·대리·사원에게 일을 맡긴 사람(최부장)으로 본다. 지나치게 보수적인 판단이다.
- v1.6.1이 놓친 항목: 최종 응답의 홍보 문구.
- 실행 시간: v2 기획 회의 실행 하나가 산출물을 390초에 완성한 뒤에도 백그라운드 작업이 남아 750초에 끝났다. 보수적으로 750초를 기록해 평균이 327초다. 산출물 완성 시점으로 보면 237초다. 어느 쪽이든 v2가 빠르다고 말할 근거는 없다.
- **0.002 차이는 실행 1회의 잡음 범위다. "더 낫다"가 아니라 "같은 수준"으로 읽어야 한다.** 게이트 M9는 기준(더 높고 0.8 이상)을 통과했지만 이 해석을 함께 기록한다.

### 점수에 잡히지 않은 차이

| 관찰 | v2 | v1.6.1 |
|------|----|--------|
| 음성 변환 스크립트 | 그대로 실행됨 | 음성 실행 6번 모두 PyAV 오류로 실패. 에이전트가 임시 래퍼를 만들어 우회(래퍼 5개가 작업 폴더에 남음, 1개는 실행 후 삭제했다고 보고) |
| 홍보 문구(최종 응답) | 0/8 | 8/8 |
| STT 교정 | `meta.corrections`로 선언, verify가 근거 확인 | 응답에 설명(검증 없음) |
| 근거 추적 | 결정·할 일마다 발언 번호, 문서 끝 대조표 | 없음 |

v1.6.1 점수가 높은 이유는 강한 모델이 스킬의 결함(경로, 깨진 STT, 필수 질문)을 스스로 우회했기 때문이다. 사람 사용자나 약한 모델은 같은 우회를 하지 못할 가능성이 크지만, 이번 평가로 측정하지는 않았다.

## 3. 정답표 수정 — 평가 후에 바꾼 것

기획 녹음의 구독 가격 정답을 평가 뒤에 19,900원에서 11,900원으로 바꿨다.

- **근거:** 같은 녹음을 다섯 가지 설정으로 변환했다. 제안 발언은 네 번이 '만천구백원'(11,900)이었다. 결정 발언은 small 11,900, medium·base+힌트 1,900('만' 누락), base만 19,900이었다(`references/stt.md` §6).
- **처음 정답(19,900)의 출처:** base 모델 한 번의 결과뿐이었다.
- **편향 방지:** 이 수정은 iteration-1에서 11,900원을 쓴 v2에 유리하다. 그래서 가격 항목은 정답 값을 채점하지 않고, "'1,900원'으로 적지 않았고 인식이 엇갈린 가격을 확인 필요로 알렸다"는 [판단] 항목으로 바꿔 두 구성을 같은 기준으로 판정했다. 두 구성 모두 통과했다.
- 같은 방식으로 스프린트 녹음의 다음 회의 시각(base '52시' → small '오후 2시')과 기획 녹음의 얼리버드 목표(1,000명)·김과장 기한(다음 주 월요일)도 정답표에 반영했다.

## 4. 만들면서 발견해 고친 결함

| 발견 경로 | 결함 | 조치 |
|-----------|------|------|
| STT 실측 | faster-whisper 1.2.1이 PyAV 19에서 `metadata_errors` 인자 오류로 mp3를 못 읽는다. 지금 새로 설치하면 누구나 겪는다(v1.6.1 음성 실행 6/6 실패로 재확인) | PyAV로 직접 디코딩. 테스트가 라이브러리 결함 여부를 기록 |
| STT 실측 | 이 PC 디스크 여유 0.3GB로 small 모델(465MB) 내려받기 실패 | 받아 둔 모델 중 가장 큰 것으로 자동 대체하고 이유를 출력. 전달 시 정확도 한계를 알리도록 verify 경고 |
| 평가 iteration-1 | 인식 힌트 기본 사용이 숫자를 망가뜨림 | `--hotwords` 선택으로 변경, 실측 표를 stt.md에 기록 |
| 평가 iteration-1 | 이메일 요약에서 기준 수치 누락 | 작성 규칙 추가 |
| 평가 iteration-1 | 날짜 미상 이메일 제목에 "(Unknown)" | 수정·테스트 |
| 정답표 작성 | 녹취록 요일 오류(2026-03-24·31은 화요일) | 23일·30일(월)로 수정 |
| verify 개발 | 요일에 붙인 계산 날짜(수요일(3/11))를 지어낸 숫자로 오판 | 숫자 검사에서 빼고 요일 대조(due-date-mismatch)로 검사 |
| 채점기 개발 | 근거 대조표(녹취 원문 인용)의 오인식을 본문 오류로 셈, 다음 회의를 제목 줄만 봄, "3월 11일(수)" 요일 미인식 | 본문만 검사, 3줄 창, 요일 약식 인식. 정리 안 한 녹취를 넣으면 6개 항목이 실패하는 대조로 확인 |

## 6. 남은 것

- 트리거 실측: CLI 로그인 필요(handoff H10). meeting-minutes용 트리거 세트도 아직 없다.
- 화자 분리: 하지 않는다. 담당자를 발언 맥락으로 추정해야 해서, 이번처럼 지나치게 보수적이거나(미정) 반대로 틀릴 수 있다. pyannote 같은 화자 분리는 무거워 선택 기능 후보로 남긴다.
- 실행 1회씩이라 분산을 모른다. 동률에 가까운 결과라 반복 측정의 가치가 크다.
