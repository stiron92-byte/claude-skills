# 용도·역할별 회의록 구성

`build_minutes.py`가 용도별 뼈대를 그린다. Claude는 minutes.json의 내용(요약 문장, 안건 요점, 추가 섹션)을 역할에 맞게 고른다.
같은 회의라도 누가 무엇에 쓰느냐에 따라 남길 것이 다르기 때문이다.

## 1. 용도별 뼈대(build_minutes.py --purpose)

| 용도 | 순서 | 분량 감각 | 근거 대조표 |
|------|------|-----------|:-----------:|
| team(팀 공유) | 핵심 요약 → 결정 → (추가 섹션) → 할 일 표 → 미결 → 다음 회의 → 확인 필요 | 한 화면. 요약 2~3줄 | md·docx 부록 |
| report(상위 보고) | 결론(요약) → 안건별 논의 → 결정 → (추가 섹션) → 다음 단계(할 일) → 리스크 → 미결 → 다음 회의 | 결론만 읽어도 판단 가능하게 | md·docx 부록 |
| personal(개인 기록) | 요약 → 안건별 상세 논의 → 결정 → (추가 섹션) → 할 일 → 미결 | 논의 맥락을 최대한 보존 | md·docx 부록 |
| email(이메일 공유) | 제목 줄 → 인사 → 요약 → 결정 → 할 일 목록 → 미결 → 다음 회의 → 맺음 | 본문에 바로 붙여 넣는 길이 | 없음 |

형식: `md`(마크다운 파일), `docx`(워드), `notion`(노션 붙여넣기용, 할 일은 `- [ ]` 체크박스), `text`(채팅·메일 본문).
결정·할 일·미결이 없으면 섹션을 지우지 않고 "없음"으로 남는다.

## 2. 역할별로 더할 것(minutes.json의 sections, summary 선택)

| 역할 | 요약에 먼저 쓸 것 | 추가 섹션(sections) 예 |
|------|-------------------|------------------------|
| PM | 일정·마일스톤 변화, 담당자 배정 | 리스크 및 이슈, 의존성 |
| 기획자 | 요구사항·우선순위 변경, 사용자 피드백 | 요구사항 변경 사항 |
| 영업 | 고객 요청, 가격·계약 조건, 후속 기한 | 고객 요청 사항, 매출·계약 영향 |
| 인사 | 채용·평가·조직·정책 결정 | 정책 변경 사항(민감 정보는 최소한으로) |
| 개발자 | 기술 결정, 버그·이슈, 기술 부채 | 기술 결정 사항, 이슈·버그 목록 |
| 디자이너 | 디자인 피드백, UX 결정, 리비전 요청 | 디자인 피드백 요약, 리비전 항목 |

추가 섹션의 문장도 숫자·이름 규칙(minutes-schema.md §4)을 따른다. 근거 발언 번호를 붙이면 근거 대조표에 나온다.

## 3. 쓰지 않는 것

- 결과물 끝의 스킬 소개·홍보 문구("이 스킬은 회의록 외에도…")
- 녹취에 없는 배경 설명, 추측한 원인, 회의에 없던 권고
- 잡담, 인사말 반복("수고하셨습니다" 등)

## 4. 노션에 붙여 넣을 때

`#` 머리말, `-` 목록, `- [ ]` 체크박스, 마크다운 표, `**굵게**`는 그대로 인식된다. HTML 태그와 노션 전용 블록(토글·콜아웃)은 쓰지 않는다.
